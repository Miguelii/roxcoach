# Lyfta Integration Implementation Plan

**Goal:** Connect a personal Lyfta account from Settings and manually import its completed gym
workouts as Roxcoach strength activities. Sync is user-triggered, repeatable and has no background
job.

**Architecture:** A protected `lyfta` tRPC module validates and encrypts the personal API key,
stores it in a service-role-only table, calls Lyfta from the server, and delegates activity writes
to the `training` service. The application orchestrates activity upserts and strength-set
replacement through session-bound Supabase writes. Settings provides connection, manual sync and
disconnect actions.

**Tech stack:** Next.js 16, React 19, tRPC, Effect v4, Supabase (`roxcoach` schema), Node
`crypto`, built-in `fetch`, Zod, PGlite, `pnpm test`. No new package is expected.

**Binding specs:** `docs/tech-specs/lyfta.md`, `database.md`, `architecture.md`,
`manual-logging.md` and `ux-design.md`. The specs win over this plan; update them in the task that
changes their contracts.

## Global constraints

- Read `AGENTS.md` and the binding specs before implementation. Follow the repo conventions:
  English code and UI copy, `@/` imports under `src/`, Effect v4, `pnpm` only, no dev server, and
  run tests with `pnpm test`, never Vitest directly.
- Never read `.env*` files. Never expose or log API keys, encryption keys, authorization headers,
  raw upstream payloads or database rows containing ciphertext.
- The Lyfta key is accepted only by a protected server mutation. Store it encrypted with
  AES-256-GCM using `NEXT_LYFTA_ENCRYPTION_KEY`; the service-role-only `lyfta_connections`
  repository is the sole database access path for credentials.
- Service-role repository functions always accept `supabase` then `userId`, explicitly filter or
  set `user_id`, and inspect both `Effect.tryPromise` failures and returned Supabase errors.
- Activity data writes run with the authenticated user's session-bound Supabase client. Never use
  the service-role client for activity or strength-set imports.
- Lyfta API requests are read-only and server-side. Do not add OAuth, webhooks, a scheduler, a
  queue, a cron route or automatic sync.
- Use only data returned for the authenticated key owner. Never accept a Lyfta client id or a user
  id from the browser as authority.
- Tests use `data-testid` selectors only. Prefer injected clients and fetch functions over module
  mocks. Run `pnpm fmt`, `pnpm check`, `pnpm knip` and `pnpm test` before handing off.
- Do not commit unless asked. If committing later, include the required Copilot co-author trailer.

## Review focus

1. Authenticated and anonymous clients cannot read or write `lyfta_connections`, including its
   ciphertext; only server-role code with an explicit user filter can access it.
2. A Lyfta API key never reaches browser state after submission, query data, logs, error payloads
   or the client-visible DTO.
3. Replacing a key with an invalid key leaves the old connection usable.
4. An invalid workout or a failed page never advances `last_synced_at`; already imported pages
   remain safe to retry without duplicates.
5. A repeated workout ID upserts the same activity and replaces only its Lyfta-owned strength
   sets. Local notes and perceived effort survive.
6. Every activity and set operation is scoped to the authenticated user; the composite foreign
   key and RLS prevent cross-user writes.
7. Imported sets are the completed ones plus those with reps or weight; malformed dates or malformed non-empty
   numeric values fail explicitly rather than disappearing silently.
8. Disconnect removes credentials but preserves the user's imported activities and sets.
9. No activity or set write can target a different user's row, even if a forged id is supplied.

### Task 2: Validate the encryption key and implement credential storage

**Files:**

  `docs/tech-specs/lyfta.md`
- Test: helper, repository and service tests under `__tests__`

**Interfaces:**

- `NEXT_LYFTA_ENCRYPTION_KEY` is optional at startup and when set must be canonical base64 for
  exactly 32 bytes. Lyfta operations fail with a stable configuration error if absent; reject a
  malformed configured value explicitly.
- Encrypt with `node:crypto` AES-256-GCM and a fresh random 12-byte nonce per value. Store a
  versioned payload containing the nonce, ciphertext and authentication tag. Decryption rejects
  unknown versions, malformed payloads and tampering without exposing plaintext or crypto error
  details.
- Repository functions use the service-role client and accept `supabase`, then `userId`.
  `selectLyftaConnection`, `upsertLyftaConnection` and `deleteLyftaConnection` explicitly scope
  every query to that user. Return only encrypted bytes to server code, never to a controller DTO.
- Connection status is `{ connected: boolean; lastSyncedAt: string | null }`.

### Task 3: Build the Lyfta API client and workout parser

**Files:**

  `services/lyfta-api.service.ts` and tests with sanitized inline payloads
- Modify: `docs/tech-specs/lyfta.md` only if verified API details require a contract correction

**Interfaces:**

- API client accepts an injected `fetch` for tests, sends `Authorization: Bearer` only in request
  headers, sets a finite timeout, and performs sequential page requests.
- Validate the envelope (`status`, pagination metadata and `workouts`) and each workout. Preserve
  Lyfta's exact `excercise_name` field spelling.
- Parser output is a normalized Lyfta workout with stable decimal-string `sourceId`, title,
  parsed instant, and only completed sets. Missing optional reps/weight become null; malformed
  non-empty values, missing exercise names, invalid IDs and invalid/ambiguous dates return
  explicit parse errors.
- The parser accepts the sandbox's ISO UTC timestamp and the observed live `YYYY-MM-DD HH:mm:ss`
  form, interpreting the latter as UTC to match Lyfta's documented UTC timeline filtering. Add
  tests for both forms and a date near a timezone boundary.
- Map 401 to invalid credentials, 429 to rate-limited, other non-2xx to upstream failure, and
  transport, timeout and JSON/schema failures to distinct internal tagged errors. Error causes
  must not retain headers, key, response body or raw workout data.

### Task 5: Implement connection, manual sync and tRPC procedures

**Files:**

- Create: `src/_bff/modules/lyfta/controllers/*.controller.ts`,
  `services/lyfta-connection.service.ts`, `sync-lyfta-workouts.service.ts`,
  `lyfta.router.ts`, service and controller tests
- Modify: `src/_bff/trpc/router.ts`, `src/_bff/modules/lyfta/services/lyfta-connection.service.ts`,
  `src/_bff/lib/errors.ts`, `src/_bff/lib/error-codes.ts`

**Procedures:**

- `lyfta.getConnectionStatus` returns only `connected` and `lastSyncedAt`.
- `lyfta.connect` validates the submitted API key with `GET /me` and
  `GET /workouts?limit=1&page=1`, encrypts only after successful validation and atomically
  replaces any previous connection.
- `lyfta.syncWorkouts` requires a connection. Initial sync paginates all workouts with limit 100;
  incremental sync starts on the UTC day before `lastSyncedAt` and ends on the current UTC day.
  It imports each normalized workout sequentially through the training service and advances
  `last_synced_at` only after every page succeeds. Partial activity writes are retained and safe
  to retry.
- `lyfta.disconnect` removes only the connection row. It leaves all training history untouched.
- All are protected tRPC controllers using exhaustive tagged error mapping. No controller returns
  the API key, encrypted payload, raw response or database error details.
